# Phases — Detailed Implementation Guide
## RFP Intelligence Platform: RAG Search Engine & Multi-Agent System

This document is the **execution guide** for implementing the project phase-by-phase.

The master architectural intent is defined in `plan.md`. This file answers:

- What exactly should be built in each phase?
- Which files/modules should be created?
- What interfaces should exist?
- What should be tested?
- What must be demonstrated before moving forward?
- What common implementation mistakes must be avoided?

---

# 0. Global Engineering Rules

These rules apply to every phase.

## Rule 0.1 — Implement incrementally

Never ask the coding agent to build the entire platform in one pass.

For every phase:

```text
Understand
   ↓
Implement
   ↓
Test
   ↓
Run on real Bid1/Bid2 data
   ↓
Inspect output
   ↓
Fix
   ↓
Document
   ↓
Commit
   ↓
Next phase
```

## Rule 0.2 — Do not break completed phases

Before modifying an existing component:

1. inspect its current implementation
2. inspect its tests
3. preserve public interfaces when practical
4. run the relevant tests before and after the change

## Rule 0.3 — Keep production logic generic

Never add logic specifically for:

- Bid1
- Bid2
- a particular supplied filename
- a particular expected answer

The supplied bids are test data.

## Rule 0.4 — Evidence must survive every stage

The eventual pipeline is:

```text
Raw File
  ↓
Document
  ↓
Page
  ↓
Table
  ↓
Chunk
  ↓
Retrieved Evidence
  ↓
Extracted Field
  ↓
Final Value
```

At every stage preserve provenance.

## Rule 0.5 — Deterministic code controls deterministic concerns

Prefer Python code for:

- discovery
- classification
- metadata
- hashing
- chunk IDs
- BM25
- RRF
- filtering
- schema validation
- retries
- date parsing
- evaluation

Use LLMs for:

- semantic query understanding
- semantic extraction
- natural-language synthesis
- semantic addendum interpretation
- semantic validation

## Rule 0.6 — Never fabricate evaluation results

All Recall/MRR/latency/extraction numbers shown in the README must be generated by the actual implementation.

## Rule 0.7 — External providers must be replaceable

Use adapters/interfaces for:

```text
LLM
Embedding
Reranker
Vector Store
```

The rest of the code should not depend directly on vendor-specific calls.

## Rule 0.8 — No secrets

Never commit:

```text
.env
API keys
tokens
credentials
private URLs
```

Only `.env.example` belongs in Git.

# PHASE 1 — Document Discovery & Ingestion

## Objective

Convert raw files into canonical documents.

Pipeline:

```text
Folder
  ↓
File Discovery
  ↓
Classification
  ↓
Parser
  ↓
Cleaning
  ↓
Metadata
  ↓
Canonical Document
```

## Modules

Create:

```text
app/ingestion/
├── discovery.py
├── classifier.py
├── pdf_parser.py
├── html_parser.py
├── table_parser.py
├── cleaner.py
├── metadata.py
├── models.py
└── service.py
```

## File Discovery

Input:

```python
discover_files(folder_path)
```

Output should include:

- resolved path
- filename
- extension
- MIME type if available
- file size
- future hash field

Ignore:

- temporary files
- unsupported files
- hidden editor artifacts

## Classification

Support:

```text
bid_page
rfp
addendum
specs
affidavit
other
```

Use generic heuristics:

- extension
- filename
- title
- content markers
- structural clues

Return:

```text
doc_type
confidence
reason
```

Uncertain files should become `other`, not crash the pipeline.

## PDF Parsing

Use:

- PyMuPDF for primary text extraction
- pdfplumber for tables
- Docling later if difficult layouts need it

Preserve:

- page number
- page text
- table blocks

## HTML Parsing

Use:

- BeautifulSoup
- trafilatura

Remove:

- scripts
- styles
- navigation
- boilerplate

Preserve useful portal metadata.

## Cleaning

Deterministically:

- normalize whitespace
- fix safe line wraps
- safely repair hyphenated words
- detect repetitive headers/footers
- preserve headings
- preserve lists
- preserve tables
- preserve page boundaries

Do not use an LLM for cleaning.

## Metadata

At document/page/table level preserve:

```text
bid_id
file_name
doc_type
addendum_number
document_date
page_number
source_path
```

Do not invent missing metadata.

Use `None`.

## Error Handling

Do not allow one broken page to terminate an entire bid.

Collect:

```text
file
page
error_type
message
```

Detect likely:

- scanned pages
- empty pages
- extraction failures

OCR can be plugged in later.

## Output

Generate:

```text
outputs/ingestion/Bid1.json
outputs/ingestion/Bid2.json
```

## CLI

Implement:

```bash
python main.py ingest --bid ./data/Bid1
python main.py ingest --bid ./data/Bid2
```

Print:

```text
Files discovered
PDF count
HTML count
Classification counts
Pages processed
Tables extracted
Warnings
Errors
Output path
```

## Tests

Create:

```text

test_classifier.py
test_pdf_parser.py
test_html_parser.py
test_table_extraction.py
test_cleaning.py
test_metadata.py
test_ingestion_service.py
```

## Acceptance Gate

- one Bid1 RFP page
- one Bid1 addendum

- Bid2 PORFP

# PHASE 2 — Canonical Documents & Chunking

## Objective

Turn canonical documents into retrieval-ready chunks.

## Chunking Strategy

Normal text:

```text
600–800 tokens
~100 token overlap
```

Use:

- heading-aware
- section-aware
- paragraph-aware
- list-aware splitting

Do not break meaningful requirement boundaries unnecessarily.

## Table Rule

Important tables should remain atomic whenever practical.

Allow larger table chunks.

## Context Breadcrumbs

Example:

```text
[Bid: Bid2]
[Document: Dell_Laptop_Specs.pdf]
[Type: specs]
[Page: 4]
[Section: Configuration]
```

This context should be embedded with the chunk.

## Chunk Model

```python
class Chunk(BaseModel):
    chunk_id: str
    bid_id: str
    file_name: str
    doc_type: str
    page_number: int
    section_title: str | None
    addendum_number: int | None
    text: str
    is_table: bool
```

## Deterministic Chunk IDs

Chunk IDs should be reproducible.

Recommended inputs:

```text
bid_id
file hash
page
section
chunk sequence
```

Do not use random IDs for indexed chunks.

## Evidence Model

```python
class Citation(BaseModel):
    file: str
    page: int
    chunk_id: str
    text: str
```

```python
class Evidence(BaseModel):
    evidence_id: str
    bid_id: str
    text: str
    citation: Citation
    doc_type: str
    addendum_number: int | None
    section: str | None
```

## Output

Generate inspectable chunks:

```text
outputs/chunks/Bid1.jsonl
outputs/chunks/Bid2.jsonl
```

## Tests

Create:

```text
test_chunking.py
test_chunk_ids.py
test_evidence_schema.py
test_table_chunks.py
```

## Acceptance Gate

Manually inspect:

- short chunk
- long chunk
- section chunk
- table chunk
- citation metadata

# PHASE 5 — Hybrid Retrieval + RRF

## Objective

Combine semantic and lexical retrieval.

## Architecture

```text
                 Query
                /     \
               /       \
          Qdrant       BM25
             |           |
             +-----+-----+
                   |
                  RRF
                   |
              Candidate set
```

## Retrieval Flow

1. receive query
2. apply metadata filters
3. dense search
4. BM25 search
5. merge results
6. calculate RRF
7. preserve all metadata
8. return candidates

## RRF

Use:

```text
RRF(d) = Σ 1 / (k + rank(d))
```

Start with:

```text
k = 60
```

Make it configurable.

## API

Implement:

```text
GET /search
```

Parameters:

```text
q
bid_id
doc_type
addendum_number
top_k
```

## Result

Each result:

```json
{
  "score": 0.0,
  "text": "...",
  "source": {
    "file": "...",
    "page": 1,
    "chunk_id": "..."
  },
  "metadata": {}
}
```

## Tests

Create:

```text
test_rrf.py
test_hybrid_retrieval.py
test_metadata_filtering.py
```

## Acceptance Gate

Test at least:

```text
"What processor is specified?"
"What is E20P4600040?"
"JA-207652"
"WD22TB4"
"deadline"
```

Verify that both semantic and exact-match queries retrieve useful evidence.

# PHASE 6 — Jina Reranking

## Objective

Improve precision after hybrid retrieval.

## Pipeline

```text
Dense top N
    +
BM25 top N
    ↓
RRF
    ↓
Top 15–20
    ↓
Jina Reranker
    ↓
Top 5
```

## Provider Interface

Create:

```python
class Reranker(Protocol):
    def rerank(query, documents, top_k)
```

Implement:

```text
JinaReranker
```

## Requirements

- API batching where useful
- timeout
- retry/backoff
- rate-limit handling
- latency measurement
- structured errors

## Failure Handling

If reranking fails:

- do not crash the entire search request
- log the failure
- use a safe fallback ranking strategy

Whether fallback is enabled in production should be configurable.

## Tests

Create:

```text

```

## Acceptance Gate

Verify the final search results preserve:

- chunk text
- file
- page

- metadata

# PHASE 8 — Incremental Indexing

## Objective

Support efficient updates.

## Registry

Maintain:

```text
file_hash
file_name
bid_id
indexed_at
chunk_ids
embedding_model
```

## Behavior

### New file

```text
parse
→ chunk
→ embed
→ vector upsert
→ BM25 update
```

### Same hash

```text
skip
```

### Changed hash

```text
delete old chunks
→ re-parse
→ re-chunk
→ re-embed
→ re-index
```

### New bid

Index only that bid.

## Important

Do not re-index every bid every time.

## Tests

Create:

```text

```

Scenarios:

1. first indexing
2. same file twice
3. modified file
4. newly introduced bid
5. deleted file if supported

Demonstrate that Bid1 does not get re-embedded when a new Bid3 is added.

# PHASE 13 — Addendum Reconciliation

## Objective

Turn source-level facts into effective bid requirements.

## Pipeline

```text
Base RFP
   ↓
Extract base values
   ↓
Retrieve addendum evidence
   ↓
Compare field-by-field
   ↓
Apply valid changes
   ↓
Effective values
```

## Model

```python
class AddendumChange(BaseModel):
    field: str
    original_value: Any
    updated_value: Any
    source: Citation
    reason: str
```

## Important Rule

Do NOT use:

```text
latest file wins
```

for every field.

Use field-dependent source authority.

## History

Every change should retain:

```text
old value
new value
source
reason
```

## Acceptance Gate

Bid1 must show:

```text
original deadline
→ addendum update
→ effective deadline
```

and the change must be represented in structured output.

# PHASE 14 — Validator + Retry Loop

## Objective

Prevent unsupported final output.

## Validation Layers

### Structural

- Pydantic schema
- required keys
- field types

### Citation

- source exists
- page exists
- chunk exists
- evidence text exists

### Format

- dates
- numeric values
- required structures

### Semantic

Use Groq when necessary:

```text
SUPPORTED
UNSUPPORTED
AMBIGUOUS
```

## Retry

On failure:

```text
Validator
   ↓
failed field
   ↓
targeted retrieval
   ↓
re-extraction
   ↓
validator
```

Default maximum:

```text
2–3 retries
```

Never allow infinite loops.

## Acceptance Gate

Create a test in which a deliberately incorrect/unsupported field is rejected.

The validator should route only that field back for another attempt.
